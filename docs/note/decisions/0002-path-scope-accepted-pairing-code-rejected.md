# ADR 0002: パススコープ制限(R7)を採用し、ペアリングコード方式(R6)は不採用とする

- **ステータス**: Accepted(R7)/ **Rejected**(R6 — 恒久的に不採用。将来の再検討には新規ADRが必要)
- **日付**: 2026-09-03
- **関連文書**: [提案書](../../auth-proxy-api-token-proposal_v1.md) §5 R6/R7、§10、§13 /
  [ADR 0001](0001-api-token-bearer-auth.md)(follow-up事項としてR6/R7を個別ADR起票後に着手、と決めていた)

---

## コンテキスト

Phase API-1(Bearerトークン認証の中核: R1・R2・R3・R5)とPhase API-2(トークン発行・失効の
Web UI: R4)は実装・レビュー・マージ済みで、下流アプリ(timetrack)はブラウザでトークンを
発行し、デスクトップアプリ側にコピー&ペーストして使う運用が既に成立している。

ADR 0001のfollow-up事項として、残るR6(ペアリングコード)・R7(パススコープ制限)は
「個別ADR起票後に着手」としていた。特にR6は**未認証で叩けるエンドポイント
(`POST /api/pairing/claim`)を新設する**ため、着手前に必要性を再確認した。

## R6(ペアリングコード方式)を採用しない判断

提案書を再確認した結果、R6は以下の理由により**必要性が薄いと判断し、不採用とする**。

1. **提案書自身が「推奨」（必須ではない）と明記している**（§4 要求機能一覧）。R1〜R3・R5のみが「必須」。
2. **提案書の実装フェーズ表（§10）でも、R6はブロッカー解消ではなく「体験と安全性が向上する」という
   位置づけ**である。Phase API-1完了時点で「timetrack側は実装を開始できる」と明記されており、
   R6はその後の話。
3. **R6の動機（§5 R6）はUXの問題のみ**: 「トークン文字列（50文字程度）を手作業でアプリに
   コピー&ペーストさせるのは、特に別マシンで発行した場合に体験が悪い」。この課題は
   Phase API-2のWeb UIによるトークン発行で既に実用上十分に緩和されている。
4. **本来解決すべきだった3つの課題**（提案書§1.2: Cookie認証が使えない・セッションTTLが
   短い・302リダイレクトでエラー処理できない）は、**Phase API-1だけで全て解決済み**であり、
   R6が無いと解決できない課題は残っていない。
5. 一方でR6を実装すると、**未認証エンドポイントというauth-proxyにとって新しい種類の
   攻撃面が増える**（総当たり対策・タイミング攻撃対策・レート制限を継続的に維持する
   コストが発生する）。UXの軽微な改善のためにこのトレードオフを払う積極的な理由がない。

現時点で「別マシンでの頻繁なペアリングが運用上の課題になっている」という具体的な
ニーズは確認されていない。**もし将来そのようなニーズが明確になった場合は、その時点の
具体的な運用課題を根拠に新しいADRを起票して再検討すること。** 本ADRはR6を
「Phase API-3として先送りにした」のではなく「実装しないと決定した」ものである。
`pairing_codes` テーブル、`POST /api/pairing/codes`・`POST /api/pairing/claim`、
`AUTH_PROXY_PAIRING_CODE_TTL_MINUTES` 環境変数は、いずれも今後作成しない。

## R7(パススコープ制限)を採用する判断

R7は不採用としない。理由:

- **新しい攻撃面を増やさない**。既存の認証済みリクエストに対する認可を"狭める"だけの
  変更であり、R6のような未認証エンドポイントの追加を伴わない。
- Phase API-1実装時点で `api_tokens.path_prefix` カラムを先行して用意済み（常にNULL）
  であり、追加のスキーマ変更が不要。
- timetrack側の実際のユースケース（`/sync/` にのみアクセスできるトークンを発行したい）
  に対応する、具体的な最小権限強化になる。

### 実装方針

- `api_tokens.path_prefix` が設定されている場合、`auth_middleware` のBearー検証成功後に
  リクエストパスがそのprefixで始まるかを確認する。外れていれば
  `403 insufficient_scope` を返す（提案書§5 R3のエラー語彙表と一致）。
- チェックは「トークンの有効性検証」の直後・「ユーザー情報取得」より前に行う
  （スコープ外アクセスの場合に無駄なDBクエリを増やさないため）。
- `path_prefix` が `NULL`（未設定）のトークンは、Phase API-1と同じく全パスにアクセス
  できる。既存の発行済みトークンの挙動に変更はない（後方互換）。
- `POST /api/tokens`(JSON API)・`/settings/security/tokens`(Web UI)の両方で、
  発行時に任意で `path_prefix` を指定できるようにする。

## 影響（Consequences）

- R6のためにADR 0001が示唆していた「未認証エンドポイントのセキュリティレビュー」は
  発生しない（R6自体を作らないため）。
- R7実装後、`docs/note/api-token-auth-runbook.md` の「フェーズ分割」表からR6を
  「不採用」に更新する。
- 提案書 `docs/auth-proxy-api-token-proposal_v1.md` 自体は提案元（timetrackプロジェクト）
  からの提案書という性質上、原文は書き換えない。本ADRが提案書のR6部分に対する
  正式な決定として優先する。

## 追記（2026-09-04）: `/security-review` で検出した指摘と対応

R7実装後に `/security-review` skill でレビューを実施し、以下1件を確認・修正した。

### パススコープが正規化前のパス文字列で判定されており、ドットセグメント越えで回避可能だった

**指摘**: `auth_middleware` のスコープ判定は `req.uri().path().starts_with(prefix)` という
生の文字列比較のみで行っていた。`http::Uri::path()` は `..` の畳み込みやパーセントデコードを
一切行わない一方、プロキシモードで下流アプリへ転送する際（`handlers/proxy.rs::forward_to_upstream`）
に組み立てる転送先URLは `reqwest` 経由で `url` クレートの `Url::parse` によって正規化され、
`..` および `%2e%2e` 等のパーセントエンコード表現も畳み込まれる。

このため `path_prefix = "/sync/"` のトークンで `GET /sync/%2e%2e/admin/users` を送ると、
生文字列としては `"/sync/"` で始まるためスコープチェックを通過するが、実際に下流アプリへ
送信されるリクエストは `Url::parse` によって `/admin/users` に正規化され、**スコープを完全に
迂回してアクセスできてしまう**。R7が保証しようとしていた最小権限が無効化される、
Highの深刻度の指摘だった。

**対応**: スコープの前方一致判定より前に、リクエストパスの各セグメントをパーセントデコードした上で
`..` と完全一致するものが無いかを確認する `contains_dot_dot_segment` を追加し、該当する場合は
即座に `403 insufficient_scope` を返すようにした（`src/middleware/auth.rs`）。
リテラルの `..` と、大文字小文字の組み合わせを含む `%2e%2e` 系のパーセントエンコード、
リテラルとエンコードが混在したセグメント（`.%2e`・`%2e.`）の両方をテストで確認済み。
既存の静的ファイル配信（`handlers/proxy.rs`）が同種の脅威に対して
`Path::components()` ベースでの `..` 拒否を既に行っていたのと同じ設計判断である。
