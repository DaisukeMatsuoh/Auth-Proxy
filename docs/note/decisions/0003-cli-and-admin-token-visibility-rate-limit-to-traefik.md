# ADR 0003: Phase API-4 — CLI(R9)と管理画面でのトークン可視化(R10)を採用、レート制限(R8)はauth-proxy本体には実装しない

- **ステータス**: Accepted(R9・R10、いずれもスコープを限定)/ **Rejected as an auth-proxy feature**(R8。Traefik側の設定に委譲)
- **日付**: 2026-09-04
- **関連文書**: [提案書](../../auth-proxy-api-token-proposal_v1.md) §5 R8/R9/R10、§10 /
  [ADR 0001](0001-api-token-bearer-auth.md) / [ADR 0002](0002-path-scope-accepted-pairing-code-rejected.md)

## コンテキスト

Phase API-1(Bearer認証)・API-2(Web UI)・API-3(R7パススコープのみ、R6は不採用)は
実装・レビュー・マージ済み。提案書§1.2が挙げていた本来の課題(Cookie認証・セッションTTL・
302リダイレクト)はPhase API-1で全て解決済みであり、残るPhase API-4(R8・R9・R10)は
提案書のフェーズ表でも「運用が成熟する」という、他フェーズより一段階優先度の低い位置づけである。

これまでの各フェーズで、機能追加のたびに`/security-review`で実質的な指摘(admin権限昇格・
反射型XSS・パススコープのトラバーサル回避×2)が見つかっている実績を踏まえ、着手前に
利用者本人へ必要性を確認した。以下はその結果である。

## 決定1: R8(レート制限)はauth-proxy本体には実装しない。Traefik側の設定に委譲する

**確認された懸念**: 「フロントにWAFが無いので、トークンを当てるまで叩き続けるような対応への
懸念がある」というもの。

**この懸念に対する技術的な検討**: APIトークンは256bit(32バイト)のランダム値であり、
総当たりで正しい値を言い当てることは計算量的に不可能である(空間サイズ 2^256)。
これはR6で不採用にしたペアリングコード(8文字・32文字種 ≒ 1.1兆通り)とは桁が全く異なり、
**レート制限の有無に関わらず「トークンを当てるまで叩き続ける」攻撃はそもそも成立しない**。
したがって提案書R8(トークン単位のレート制限)を実装しても、確認された懸念には対応できない。

**採用する対応**: 汎用的な「叩き続けられることへの不安」への対応は、auth-proxyの既存の
設計思想(TLS終端・高度なルーティングはTraefik等に委譲し、認証のみに特化する)に従い、
**Traefikのレート制限ミドルウェアの設定に委譲する**。これによりauth-proxy本体には
新しいコード(=新しい状態管理・新しい攻撃面)を一切追加しない。README/運用ドキュメントに
Traefik側の設定例を追記する。

**スコープ外の関連トピック**: 「本当に総当たりが成立しうる入り口」は256bitトークンではなく
`/login`のパスワード認証である。現状500msの遅延はあるが試行回数によるロックアウトは無い。
これはPhase API-4(APIトークン機能)とは無関係の既存機能の話であり、**本ADRのスコープ外**。
必要であれば別途起票する。

## 決定2: R9(CLIサブコマンド)を実装する。ただしトークンの入力は一切受け付けない設計とする

**確認されたニーズ**: 「CIでの自動化に価値があれば入れておきたい。ただしセキュリティ的に
穴が開くのは嫌」というもの。

**採用理由**: CLIコマンドは既存の`init-admin`・`hash`・`list`と同じ信頼境界(ローカルマシン・
DB直接アクセスが前提)で動作するため、**ネットワーク越しの新しい攻撃面を増やさない**。
既存のHTTPエンドポイント(`/api/tokens`・`/settings/security/tokens`)とロジックを共有
(`ApiTokenStoreDb`をそのまま呼ぶ)するため、認可ロジックの二重実装によるドリフトも起きない
(CLIはOS権限のみを前提とし、`auth_method`のようなHTTP側の概念を持ち込まない)。

**実装するコマンド**:

```bash
auth-proxy token list [--user <username>]              # 一覧(ハッシュ・平文は表示しない)
auth-proxy token revoke <id>                            # 失効
auth-proxy token create --user <username> --name <name> [--path-prefix </sync/>]
                                                         # 発行。平文トークンを標準出力に1回だけ表示
```

**セキュリティ上の設計制約**:
- `token create`は**トークンを引数として受け取らない**(発行のみ)。既存の秘密情報を
  CLI引数で受け渡す設計は、シェル履歴や`ps`コマンドでの漏洩経路になるため採用しない。
- 発行された平文トークンは標準出力に1回だけ表示し、Web UI発行時と同じ「二度と表示されない」
  旨の警告を出す。
- **CI利用時の注意をドキュメント化する**: 標準出力に平文トークンが出るため、CIのログが
  マスクされていない場合はログ経由の漏洩経路になりうる。README/runbookに明記する
  (コード側だけでは解決できない運用上の注意点のため)。
- `--user`は既存ユーザー名を指定する形とし、CLI操作でユーザーを自動作成したりはしない
  (責務を混在させない)。

## 決定3: R10(管理画面でのトークン可視化)を実装する。スコープは「トークンの一覧・失効」のみに限定する

**確認されたニーズ**: 「各部署の管理者を立てて運用したい。将来的に非エンジニアでも管理画面の
通常オペレーションを行えるようにしたい」というもの。複数管理者・ユーザーの出入りが
将来的にある前提で、退職者のトークン失効漏れを防ぐ運用上の必要性が確認された。

**スコープの明確化**: 上記のニーズは実質的に「管理画面全体を非エンジニア向けに使いやすくする」
という、本フェーズより大きい話を含んでいる。**本ADRで採用するのはR10本来のスコープ
(adminが全ユーザーのトークンを一覧・失効できること)のみ**とし、管理画面全体のUX改善
(非エンジニア向けの導線整理等)は別の取り組みとして切り出す。混在させると本フェーズの
レビュー範囲が際限なく広がるため。

**実装方針**:
- `GET /admin/tokens`: 全ユーザーのトークンを一覧表示(所有者ユーザー名・名前・スコープ・
  最終利用・作成日・失効ボタン)。既存の`/admin/*`と同じ`role != "admin" || auth_method != "session"`
  ガードを適用する(Phase API-1で確立した、adminトークンによる管理画面乗っ取り防止パターンを
  そのまま踏襲)。
- `POST /admin/tokens/{id}/revoke`: 任意のユーザーのトークンを失効。
- **`ApiTokenStoreDb::revoke`は所有者チェック(`user_id`一致)を必須としているため流用できない。
  新規に`revoke_any(id) -> Result<bool, ApiTokenDbError>`を追加し、所有者チェックを行わない。**
  この関数は上記のadmin専用ガード付きハンドラーからのみ呼び出すこと。他のハンドラーから
  誤って呼ばれると、ユーザーが他人のトークンを失効できてしまう権限昇格になるため、
  呼び出し箇所は`src/handlers/admin/`配下に限定する。
- `/admin`ダッシュボードに「APIトークン管理」へのリンクを追加する。

## 影響(Consequences)

### 良い影響
- R9・R10とも、既存のセキュリティモデル(session-only admin gate、SQL側の所有権チェック)を
  そのまま再利用するため、新しい脆弱性クラスを持ち込むリスクが低い。
- R8を実装しないことで、auth-proxy本体のコード量・状態管理・テスト対象を増やさずに済む。

### 悪い影響・リスク
- `revoke_any`という「所有者チェックなしの失効」関数を新設するため、**呼び出し箇所を
  admin専用ガード付きハンドラーに限定する**という運用規律が今後も守られる必要がある
  (CLAUDE.mdに不変条件として明記する)。
- Traefikへの委譲(決定1)は、Traefikを使わないデプロイ構成(単一バイナリ・systemd運用等)
  では効かない。その場合の代替手段が必要になれば、その時点で別途検討する。

## フォローアップが必要な未決事項
- `/login`のパスワード試行回数ロックアウト(本ADRのスコープ外、別途起票を検討)
- 管理画面全体の非エンジニア向けUX改善(本ADRのスコープ外、別の取り組みとして起票する)
- Traefikを使わないデプロイでのレート制限手段(必要になった時点で検討)
