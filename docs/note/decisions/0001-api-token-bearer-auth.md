# ADR 0001: API クライアント向け Bearer トークン認証の追加

- **ステータス**: Accepted（Phase API-1 実装済み。セキュリティレビューで検出された指摘は対応済み — 末尾の「追記」参照）
- **日付**: 2026-09-03
- **関連文書**: [提案書](../../auth-proxy-api-token-proposal_v1.md) / [実装Runbook](../api-token-auth-runbook.md)

---

## コンテキスト

auth-proxy は現在、セッションCookie認証とゲストトークン認証（※後者は提案段階で、実コードには
未実装）の2経路のみを持ち、いずれもブラウザを前提としている。

timetrack プロジェクトがオフライン記録用のネイティブ常駐アプリ（Mac/Windows）を持つ構成に
変更されたことで、以下の課題が発生した。

1. Cookie ベース認証はネイティブアプリで扱いにくい（Cookie jar 実装、`SameSite=Strict`、
   リダイレクト追従を独自実装する必要がある）
2. セッション TTL（デフォルト8時間）が常駐アプリには短すぎる
3. 認証失敗時の `302 → /login` はAPIクライアントにとってエラーハンドリング不能な挙動

検討され不採用となった代替案（詳細は提案書§1.3）:

- **ゲストトークンの流用**: `X-Auth-User-Id` が紐づかず、誰のログか判別できない。
  かつ本来「共有リンク用」の機能であり意味論的に不適切
- **auth-proxy をバイパスして上流に直接ルーティング**: 上流サービスがポートを公開する
  必要が生じ、auth-proxy の中核設計思想（ネットワーク隔離による偽装防止）が崩れる。
  「上流サービスの認証負担ゼロ」という思想にも反する

## 決定

**auth-proxy に `Authorization: Bearer <token>` によるAPIトークン認証を追加する。**
ただし一度に全機能を実装するのではなく、以下の通り段階的に導入する。

### 決定1: Phase API-1（本ADRの直接のスコープ）は R1・R2・R3・R5 に限定する

- R1: Bearer トークン認証ミドルウェア（`auth_middleware` の先頭に挿入）
- R2: `api_tokens` テーブル（トークンのハッシュ・所有者・失効状態管理）
- R3: API クライアント向けエラー応答（401 JSON、RFC 6750 語彙）
- R5: `X-Auth-Method` / `X-Auth-Token-Name` ヘッダー

R4（Web UI での発行・失効）は別フェーズ（Phase API-2）とする。timetrack 側は
開発環境で `api_tokens` テーブルへ直接 INSERT することで Phase API-1 完了時点から
開発を開始できるため、UI 完成を待つ必要がない（提案書§10）。

R6（ペアリングコード）・R7（パススコープ制限）・R8（レート制限）・R9（CLI）・R10（管理画面）は
「推奨」「任意」に位置づけられており、timetrack 側の実装ブロッカーではない。これらは
それぞれ独立したセキュリティ・運用上の判断（特にR6は未認証エンドポイントの追加、
R8はDoS耐性に関わる）を要するため、**個別のADRを起票してから着手する**。本ADRでは承認しない。

### 決定2: トークンのハッシュ方式は SHA-256（Argon2id は使わない）

パスワードとAPIトークンではエントロピー・検証頻度・脅威モデルが異なるため、意図的に
既存のパスワード保存方針（Argon2id）から逸脱する。

| | パスワード | APIトークン |
|---|---|---|
| エントロピー | 低い（人間が作る） | 高い（256bit の暗号学的乱数） |
| 総当たり攻撃の現実性 | あり | 計算量的に不可能 |
| 検証頻度 | ログイン時のみ | 全リクエスト（高頻度） |
| 適切なハッシュ | Argon2id（意図的に低速） | SHA-256（高速） |

Argon2id を256bit乱数トークンに適用しても得られる安全性の向上はほぼゼロである一方、
全リクエストに数十〜数百msの遅延が乗る。これは auth-proxy の「ノンブロッキング」
「非力なハードウェアでも動作」という設計思想（`auth-proxy-spec_v10.md`）に反する。
SHA-256でも、DB漏洩時に平文トークンが復元できないという保護は維持される。

### 決定3: 既存の `AuthUser` 構造体を拡張する。新しい `AuthContext` enum は導入しない

CLAUDE.md はアーキテクチャ節で `AuthContext::Authenticated` / `AuthContext::Guest` という
enum ベースの設計を記述しているが、**実際の dev ブランチのコードはこの enum を持たず**、
`middleware/admin.rs` で定義された単純な `AuthUser { id, username, role }` 構造体を
`Extension<AuthUser>` として各ハンドラーに渡す設計になっている（ゲストトークン機能自体が
未実装であるため、`AuthContext::Guest` に相当する分岐も存在しない）。

このため本機能では、認証方式を区別する `auth_method: String`（`"session"` / `"token"`）と
`token_name: Option<String>` を **既存の `AuthUser` に追加する** 方式を採る。新しい抽象
（enum、trait等）を導入せず、既存の構築箇所（`middleware/auth.rs` 1箇所）だけを更新すれば
済むようにし、変更の影響範囲を最小化する。

将来ゲストトークン機能が実装される際に3方式（session/token/guest）を扱う必要が生じたら、
その時点で `AuthUser` → enum への再設計を検討する。今回は先回りしない（YAGNI）。

### 決定4: エラー語彙は RFC 6750（OAuth 2.0 Bearer Token Usage）に揃えるが、OAuth 2.0 / OIDC は実装しない

`invalid_token` / `insufficient_scope` などの語彙のみ流用する。認可サーバーとしての責務
（第三者アプリへの権限委譲）は現時点で不要であり、「単一バイナリ・外部サービス不要」という
設計思想と緊張関係にあるため、フルスタックのOAuth実装は却下する（提案書§12.2）。
語彙だけ揃えておくことで、将来の拡張時の互換性は確保する。

### 決定5: 機能はデフォルト無効（オプトイン）とする

`AUTH_PROXY_API_TOKEN_ENABLED`（デフォルト `false`）。既存利用者にとって、アップデートで
認証経路が無言で増えることは予期しない挙動変更になるため、明示的な opt-in を必須とする。

### 決定6: `last_used_at` はアトミックな条件付きUPDATEでスロットリングする

毎リクエストでUPDATEを発行するとSQLiteの書き込みロックが頻発し「ノンブロッキング」の
設計思想に反する。バックグラウンドバッファリング（別スレッド/タスクでの遅延書き込み）ではなく、
**`WHERE last_used_at IS NULL OR last_used_at < datetime('now', '-5 minutes')` という
SQL側の条件だけで間引く**、よりシンプルな方式を採る。実装・テストのコストが低く、
CLAUDE.mdの「`use_count`はSQL側でアトミックに」という既存方針とも整合する。

## 検討した代替案（不採用）

| 案 | 不採用理由 |
|---|---|
| ゲストトークンを長期トークンとして流用 | `X-Auth-User-Id`が付与されずユーザー識別不能。意味論的に「共有リンク」機能であり別用途 |
| auth-proxyをバイパスして上流に直接ルーティング | ネットワーク隔離という中核設計思想が崩れる。上流に認証実装責任が発生する |
| Argon2idでトークンをハッシュ | 高エントロピーな乱数に対しては安全性向上がほぼゼロな一方、全リクエストに遅延が乗る |
| OAuth 2.0 / OIDC のフル実装 | 認可サーバーとしての責務を負うことになり、単一バイナリ・外部サービス不要という設計思想に反する。今回必要なのは長期トークンでの認証のみで、第三者への権限委譲は不要 |
| `AuthContext` enum を新規導入して3方式を統一的に表現 | 現状ゲストトークンが未実装であり、抽象化の恩恵を受ける2つ目のバリアントが存在しない時点での先回り設計になる。実装コストと変更範囲が不必要に増える |

## 影響（Consequences）

### 良い影響

- ブラウザ以外のクライアント（デスクトップアプリ・CLI・CI）が auth-proxy 配下のサービスを
  利用できるようになり、timetrack の同期APIブロッカーが解消する
- 既存機能への後方互換性は完全に維持される（追加のみ、デフォルト無効）
- 上流サービスは引き続き認証実装を一切持たなくてよい（`X-Auth-*` を読むだけ）

### 悪い影響・リスク

- **新たな攻撃面**: `X-Auth-Method` / `X-Auth-Token-Name` という新規ヘッダーが追加されるため、
  既存の「クライアント由来 `X-Auth-*` ヘッダーの除去」ロジックをこの2種にも拡張しなければ、
  ヘッダーインジェクション経由の権限昇格が発生しうる。Runbook §3.7 で明示的に対応する
- `X-Auth-Token-Name` はユーザーが自由に設定するトークン名をそのままヘッダー値にするため、
  改行・制御文字のサニタイズを怠ると HTTP ヘッダーインジェクションになりうる。Runbook で
  `sanitize_header_value` として明示的に実装する
- Phase API-1 完了時点ではトークンの発行・失効に Web UI がなく、DB直接操作 or 後続フェーズの
  実装が必要（運用上の一時的な制約として許容する）
- 本ADRのスコープ外である R6（ペアリングコード）は将来 **未認証で叩けるエンドポイント**を
  追加することになり、既存のセキュリティモデルに対する追加的なレビューが必要になる。
  着手時に必ず別ADRを起票すること

### 前提条件（本ADRとは独立）

- 現在 dev ブランチの `src/handlers/me.rs` に構文エラーがあり `cargo build` が失敗する
  （Runbook §0.1）。本機能の実装着手前に別途修正が必要。この修正自体は本ADRの決定事項に
  含まれない

## 追記（2026-09-03）: `/security-review` で検出した指摘と対応

Phase API-1 実装後に `/security-review` skill でレビューを実施し、以下2件を確認・修正した。

### 1. 【重要・修正済み】API トークンが `/admin/*` に対しても有効になっていた

**指摘**: `auth_middleware` はトークン認証成功時も `AuthUser.role` に実際のDB上のロールをそのまま
設定するが、`/admin/*` 配下の全ハンドラーは `auth_user.role == "admin"` のみを見ており、
`auth_method`（session か token か）を区別していなかった。結果として、admin ユーザーが
（上流アプリ用に）自分で発行した API トークンが漏洩すると、新規admin作成・任意ユーザーの
パスワードリセット・ユーザー削除など、auth-proxy の管理画面そのものを乗っ取られる状態になっていた。

これは決定3で述べた「`AuthUser` を素朴に拡張する」設計の見落としであり、
「トークンは上流アプリへの認証専用であるべき」という本ADRの前提（§コンテキスト、§2）に反する。

**対応**: `src/handlers/admin/*.rs` の全ハンドラー（および未配線だった `middleware/admin.rs`
内の `admin_middleware`）の権限チェックを
`if auth_user.role != "admin" || auth_user.auth_method != "session"` に変更。
回帰テストを `handlers/admin/dashboard.rs` と `handlers/admin/users.rs` に追加し、
token 認証済みの admin ロールユーザーが `/admin/*` へアクセスすると403になることを確認した。

CLAUDE.md の Key Invariants に「`/admin/*` requires session authentication, not just
`role == "admin"`」として追記済み。

### 2. 【本ブランチ起因ではないが、ついでに修正】`return_to` の反射型XSS

`src/handlers/settings/security.rs`（`build_back_link`、`show_password` の `hidden_return_to`）
および `src/handlers/me.rs`（未配線の `render_guest_notice`）が、HTML属性（`href="..."` /
`value="..."`）に埋め込む文字列のエスケープに `html_escape::encode_text` を使っていた。
この関数は `&`/`<`/`>` のみをエスケープし `"` をエスケープしないため、`validate_return_to`
が `"` を弾かないことと組み合わさり、`return_to=/x" autofocus onfocus="alert(1)` のような値で
属性からの脱出が可能だった（反射型XSS）。

`git diff origin/dev...HEAD` で確認した限り、このコード自体は本ブランチで新規に導入されたもの
ではなく `origin/dev`（コミット `cc2e716`）に既に存在していたため、本来は本ADRのスコープ外だが、
実装済みコードとして手を入れられる状態だったため、ついでに `html_escape::encode_double_quoted_attribute`
（`"` も含めて適切にエスケープする関数）に置き換えて修正した。回帰テストを3箇所に追加済み。
